# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Monorepo

npm workspaces (`apps/*`, `packages/*`) with a single root `package-lock.json`. Always run `npm install` from the root, never inside an app.

- `apps/institucional` (`@geas/institucional`) — public static site, Astro 6 + Tailwind CSS v4, `escoteirosalbert.com.br`.
- `apps/gestao` (`@geas/gestao`) — internal app "Gestão", Next.js (App Router, Server Actions) + Supabase, with one module per route prefix: Financeiro (`/financeiro/...`) and Inventário (`/inventario/...`). Needs a Node server; cannot be deployed as static files. Consolidation plan and phases: `docs/consolidacao-gestao.md`.
- `packages/ui` (`@geas/ui`) — shared UI of the internal app, consumed as TS source (no build step).

## Commands (from root)

```bash
npm run dev                 # gestao + site in one terminal (concurrently); gestao needs infra:start
npm run dev:institucional   # Astro dev server at localhost:4321
npm run dev:gestao          # Next dev server at localhost:3000
npm run build               # build all apps
npm run lint                # lint all apps
npm test                    # vitest (gestao)
npm run test:db             # pgTAP + SQL scripts (supabase test db, local Supabase)
npm run test:e2e            # Playwright, desktop Chromium, own next dev on :3210 (E2E_PORT=3000 reuses a running dev server)
npm run typecheck
npm run infra:start         # local Supabase (Docker) + writes apps/gestao/.env.local
npm run db:types --workspace=@geas/gestao   # regenerate lib/server/supabase/database.types.ts after a migration
```

Per app: `npm run <script> --workspace=@geas/<app>`.

## gestao

- Layout: `app/(gestao)` (Início `/`: what needs attention in both modules plus one card per module, data from `lib/server/finance/home.ts` and `lib/server/inventory/overview.ts`; header `components/shell/gestao-header.tsx`; `/login`, `/auth`, `/usuarios`) and one route group per module (`app/(financeiro)/financeiro/...`, `app/(inventario)/inventario/...`), each with its own root layout (`RootHtml` in `components/shell/root-layout.tsx`) that sets `<html data-app>`; crossing modules is a full page load. Unknown URLs: `app/global-not-found.tsx`. Pre-consolidation finance URLs (`/lancamentos/...` etc.) redirect in `next.config.ts`.
- Code per module: pure domain in `lib/finance/` and `lib/inventory/`, components in `components/finance/` and `components/inventory/`; shared at the root (`lib/money.ts` (`parseMoneyToCents` reads `1.234,56`, `R$`; `allowNegative`), `lib/format.ts` (`money` takes reais, `formatCents` cents), `lib/auth.ts`, `lib/action.ts`, `components/shell/`).
- **Data layer (`lib/server/`)**: the only code that talks to the database. Only `lib/server/supabase/**` imports `@supabase/*` (ESLint `no-restricted-imports`, error in the whole app; off only in `lib/server/**`, `e2e/**`, `scripts/**`). Screens and actions call use-case functions in `lib/server/<module>/*.ts` (`lib/server/finance/{registry,associates,entries,attachments,reconciliation,statements,fees,debts,reports,home}.ts`, `lib/server/inventory/{locations,families,materials,movements,overview}.ts`, `lib/server/users.ts`; storage in `lib/server/files.ts`) with `member.db` (opaque `Db`, RLS as the user); never build queries in pages. Data modules take typed input, return domain types (`lib/inventory/model.ts`, row types such as `lib/finance/entry-rows.ts`; client components import types/constants from `lib/finance` or `lib/inventory`, never values from `lib/server`), throw `DataError`, and don't import `next/*`. Validation (`InputError`), `revalidatePath` and `redirect` stay in the action; `runAction(guard, work)` in `lib/action.ts` turns errors into `ActionResult`. Writes are the audited SQL functions via `rpc()` (argument names checked against generated types). New queries use `sb(db)` (typed); finance queries moved as-is use `untyped(db)`. `serviceDb()`/`serviceClient()` (secret key) only in `lib/server/users.ts` and scripts. Auth (code, link, sign-out, proxy refresh) only through `lib/server/auth.ts`.
- Session: `lib/server/session.ts` is the only file that reads `memberships`. `Member` has `db`, `user { id, email }`, `isAdmin`, `finance { role, canEdit }` and `inventory { role, canEdit, canManage }`; guards `pageSession`, `pageMember`, `memberOrError`, `financeEditorOrError`, `inventoryEditorOrError`, `inventoryManagerOrError`, `adminOrError`, `requireFinanceEditor`, `requireAdmin`.

## gestao › financeiro

- Supabase Auth passwordless, restricted to `@escoteirosalbert.com.br`; RLS per group.
- Money stored as integer cents (`lib/money.ts`).
- Migrations in `supabase/migrations/`.
- Model (glossary in `apps/gestao/docs/modelo.md`): `ledger_entries` = entry (date, `name` shown as "Histórico", account, payment method, `document_filed`, total); `entry_splits` = per-category split with description and optional associate; `statement_lines` = imported OFX lines (`external_id` = FITID, "ID OFX"), linked to entries via `reconciliation_links`. `categories.code` is derived from `parent_id` + `position` by `renumber_categories` (036): never write or hard-code it (except roots `1`/`2`); reference rubricas by id. The Rubricas screen is a client draft (`lib/category-draft.ts`) saved in one call to `save_category_tree`. `categories.ledger_code` / `accounts.ledger_code` = accounting chart code (domain `ledger_code`, mask `0.0.0.0.0000`, mirrored in `lib/ledger-code.ts`).
- All writes go through audited SQL functions (no direct write policies on catalogs, accounts, entries or statement tables). List views read `ledger_entry_rows` / `entry_split_rows` (security_invoker, with `external_ids` and `search_text`).
- Paths below under `lib/` are in `lib/finance/` unless they are the shared ones listed in the gestao section.
- Statement import is OFX-only; the CSV statement import code was removed for good (`lib/csv-reader.ts` is only the generic reader for the associates CSV import). Exports: column definitions in `lib/export/columns.ts`, rendered as XLSX or CSV; accounting CSV at `/financeiro/exportar/contabil` (see `docs/contabilidade.md`).
- SQL tests: `supabase/tests/*.sql`, run inside a rolled-back transaction (see each file's header).
- Routes: module = 1st segment, menu item = 2nd, header tab = 3rd (`/financeiro/lancamentos/movimentacoes|detalhamento|realizado`, `/financeiro/extrato/conciliar|importar`, `/financeiro/mensalidades/controle|devedores`, `/financeiro/configuracoes/<aba>`, `/financeiro/configuracoes/associados`); query string only for filters and display modes. Area roots redirect to the first tab; the module root `/financeiro` is the finance Resumo (year totals, account balances today, month by month, recent entries, overdue fees) and the menu starts with "Resumo". Every finance page header gets "Financeiro" after Início in the breadcrumbs (wrapper `PageHeader` in `components/finance/nav/page-header.tsx`). Movimentações and Detalhamento share `app/(financeiro)/financeiro/lancamentos/entries-screen.tsx`; `voltar` carries the list path + filters (`listHref` in `lib/entries.ts`). The `rubrica` filter is compact (`id` = subtree, `-id` = excluded subtree; `encodeCategorySelection`).
- Screens: every page header uses `PageHeader` (`components/finance/nav/page-header.tsx`: title, `SectionTabs` beside it, actions on the right, description, filter rows as children) inside `PageBody`/`PAGE_BODY`; never hand-roll an `<h1>` row. Every page except Início passes `crumbs` (path after Início, ending in the current page; `settingsCrumbs`/`extratoCrumbs` helpers); links back carry the filters. Breadcrumbs keep the title in the same place on every page; no separate "Voltar" link. Início has no breadcrumbs and a screen-reader-only title (`hideTitle`): only the actions row shows.
- Forms: every input, select and textarea has a visible label (`<Label htmlFor>`). Placeholders only show examples, never replace the label; `sr-only`/`aria-label` alone is not enough. Exception: search fields with the magnifier icon keep only `aria-label` and a placeholder. In editable table rows, the visible column header is the label (keep a specific `sr-only` label per row).
- `npx supabase migration up` applies new migrations without resetting local data.

## gestao › inventario

- Model and vocabulary in `apps/gestao/docs/inventario/modelo.md` (material by unit with tag `GEAS-000-0000` or by lot; divisions as a tree; families with 3-digit code; movements with review status). Migrations in `supabase/migrations/` (`032_inventory_catalog.sql`); pgTAP in `supabase/tests/inventory.test.sql`; e2e in `e2e/inventory.e2e.ts` (manager, chief, viewer).
- Roles: group admin (`memberships.role = 'admin'`) is manager in both modules; otherwise `memberships.inventory_role` (`manager` = gestor, `chief` = chefe, whose movements start `pendente`, `viewer`). Admin sets both roles in the shared `/usuarios`.
- All reads and writes through `lib/server/inventory/*` (writes are the `inventory_*` SQL functions); no direct write policies. Lists read `inventory_material_rows`, `inventory_stock_by_location` and `inventory_location_paths`.
- Routes: `/inventario` (Resumo; menu starts with "Resumo"), `/inventario/materiais` (list by location: one tab per root division, subdivisions as group rows; `/novo`, `/[id]`, `/[id]/editar`), `/inventario/movimentacoes`; Configurações (gear) with tabs `/inventario/configuracoes/divisoes|familias` (`components/inventory/settings-tabs.tsx`). Read errors show `app/(inventario)/inventario/error.tsx`.
- Division order is chosen by the manager by dragging (`inventory_locations.position`, `inventory_place_location` 037: before/after/inside, saved on drop), never alphabetical: sort by `sort_key` from `inventory_location_paths` (`treeOrder` in `lib/inventory/locations.ts`).
- Dev data from the group's spreadsheet: `apps/gestao/scripts/inventory/planilha-para-csv.mjs` then `importar-planilha.mjs` (local Supabase only; wipes and reloads the group's inventory). The CSVs are group data: never commit them.

## Shared UI (`packages/ui`, `@geas/ui`)

- Same identity in every internal app: build screens from `@geas/ui`, never hand-rolled CSS classes or app-local copies of primitives.
- `@geas/ui` (root export): app shell — `AppBrand` (module switcher: `current` is `gestao | financeiro | inventario`, logo goes to `homeHref`), `AppLogin`/`AppLoginForm`, `AppHeader`, `UserMenu`, `PageHeader`, `PageBody`, `SectionTabs` (pill buttons; below `sm` a menu button with the active tab, `components/section-tabs-menu`); `AppHeader` shows a menu button (`components/app-nav-menu`) below 1024px; `utilities` are `{ href, label, icon, active }`.
- `@geas/ui/components/<name>`: shadcn/ui (`base-mira`, Base UI primitives — not Radix) plus `section-card`, `stat-card` (`StatCard`, `ListCard`), `option-controls` (`OptionSelect`, `OptionCombobox`) and `tree-drag` (`useTreeDrag`, `DragHandle`: drag rows of a tree table before/after/inside; used by Rubricas and Divisões). Reorder only by dragging: no up/down arrows. Add shadcn components with `npx shadcn@latest add <name>` inside `packages/ui`. Imports inside the package use `@geas/ui/...` (self-reference), never `@/`.
- `@geas/ui/lib/utils` (`cn`) and `@geas/ui/lib/use-action-toast` (Server Action result → toast).
- Users: `@geas/ui/lib/roles` (domain, group/inventory roles) and `@geas/ui/components/users-manager` (screen with one role column per module). Data (list, invite, roles, remove) is `apps/gestao/lib/server/users.ts`; `/usuarios` actions check the admin and revalidate. `@geas/ui` has no database code.
- Theme: each app's `app/globals.css` starts with `@import "@geas/ui/theme.css"` (Tailwind, tokens, shell CSS in `@layer components`, legacy CSS in `@layer legacy` below utilities) and the root `<html>` carries `data-app="gestao" | "financeiro" | "inventario"` (in gestao, set by each module root layout), which sets the accent (`--app` → `primary`/`accent`: purple / dark orange).

## CI/CD

`.github/workflows/ci.yml` runs on push to `main` and on PRs: job `checks` (lint, typecheck incl. `astro check`, vitest, build) and job `db-e2e` (local Supabase via CLI 3.1.0, `supabase test db`, Playwright). No CD for the site: it is deployed by manual FTP to a host we don't own; don't add deploy steps or rely on host config files like `_redirects`.

Production database: Supabase's GitHub integration applies the migrations folder configured in its dashboard when `main` changes (it does not wait for CI). The folder is now `apps/gestao/supabase/migrations`; the dashboard path must be switched from `apps/financeiro/...` in the same merge that brings the rename to `main`. Hosting of the internal app is under evaluation and will not be Vercel: don't add deploy steps or host-specific config. Production auth settings live in the dashboard; never `supabase config push` (`config.toml` is local only). Today the Next apps still deploy on Vercel (transition).
