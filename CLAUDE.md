# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Codebase Overview

Monorepo of Grupo Escoteiro Albert Schweitzer: a public static site and an internal management app (Financeiro + Inventário + Associados) on Supabase, sharing a UI package.

**Stack**: Astro 7 + Tailwind v4 (site); Next.js 16 App Router + Server Actions, Supabase (Postgres 17, RLS, audited SQL functions, Auth OTP, Storage), shadcn/ui on Base UI (internal app); Vitest, pgTAP, Playwright.
**Structure**: `apps/institucional`, `apps/gestao` (`app/` routes, `components/`, `lib/{finance,inventory,associates,server}`, `supabase/`), `packages/ui`.

For detailed architecture (route table, data layer, migrations, data flows, gotchas), see [docs/CODEBASE_MAP.md](docs/CODEBASE_MAP.md).

## Monorepo

npm workspaces (`apps/*`, `packages/*`) with a single root `package-lock.json`. Always run `npm install` from the root, never inside an app.

- `apps/institucional` (`@geas/institucional`) — public static site, Astro 7 + Tailwind CSS v4, `escoteirosalbert.com.br`.
- `apps/gestao` (`@geas/gestao`) — internal app "Gestão", Next.js (App Router, Server Actions) + Supabase, with one module per route prefix: Financeiro (`/financeiro/...`), Inventário (`/inventario/...`) and Associados (`/associados/...`). Needs a Node server; cannot be deployed as static files. Consolidation plan and phases: `docs/consolidacao-gestao.md`.
- `packages/ui` (`@geas/ui`) — shared UI of the internal app, consumed as TS source (no build step).

## Commands (from root)

```bash
npm run dev                 # gestao + site in one terminal (concurrently); gestao needs infra:start
npm run dev:institucional   # Astro dev server at localhost:4321
npm run dev:gestao          # Next dev server at localhost:3000
npm run build               # build all apps
npm run lint                # lint all apps
npm test                    # vitest (gestao)
npm run test:db             # pgTAP + SQL scripts (supabase test db, local Supabase)
npm run test:e2e            # Playwright, desktop Chromium, own next dev on :3210 (E2E_PORT=3000 reuses a running dev server)
npm run typecheck
npm run infra:start         # local Supabase (Docker) + writes apps/gestao/.env.local
npm run db:types --workspace=@geas/gestao   # regenerate lib/server/supabase/database.types.ts after a migration
```

Per app: `npm run <script> --workspace=@geas/<app>`.

## gestao

- Layout: `app/(gestao)` (Início `/`: what needs attention in the modules (associates: control pendencies, records expiring in 30 days), associates birthdays and promise anniversaries (5 days back to 15 ahead) and branch transitions (rules in `TRANSITIONS`, `lib/associates/alerts.ts`: warning, critical and "transição iniciada" levels by age in months; late ones also counted in "Precisa de atenção"), plus one card per module; data from `lib/server/finance/home.ts`, `lib/server/inventory/overview.ts` and `lib/server/associates/home.ts`; header `components/shell/gestao-header.tsx`; `/rapido` (Registro rápido, below); `/login`, `/auth`, `/usuarios`) and one route group per module (`app/(financeiro)/financeiro/...`, `app/(inventario)/inventario/...`, `app/(associados)/associados/...`), each with its own root layout (`RootHtml` in `components/shell/root-layout.tsx`) that sets `<html data-app>`; crossing modules is a full page load. Unknown URLs: `app/global-not-found.tsx`. Pre-consolidation finance URLs (`/lancamentos/...` etc.) redirect in `next.config.ts`.
- Code per module: pure domain in `lib/finance/`, `lib/inventory/` and `lib/associates/`, components in `components/finance/`, `components/inventory/` and `components/associates/`; shared at the root (`lib/money.ts` (`parseMoneyToCents` reads `1.234,56`, `R$`; `allowNegative`), `lib/format.ts` (`money` takes reais, `formatCents` cents), `lib/auth.ts`, `lib/action.ts`, `components/shell/`).
- **Data layer (`lib/server/`)**: the only code that talks to the database. Only `lib/server/supabase/**` imports `@supabase/*` (ESLint `no-restricted-imports`, error in the whole app; off only in `lib/server/**`, `e2e/**`, `scripts/**`). Screens and actions call use-case functions in `lib/server/<module>/*.ts` (`lib/server/finance/{registry,associates,entries,attachments,reconciliation,statements,fees,debts,reports,home}.ts`, `lib/server/inventory/{locations,families,materials,movements,overview}.ts`, `lib/server/associates/{associates,sections,functions,relatives,controls}.ts`, `lib/server/users.ts`; storage in `lib/server/files.ts`) with `member.db` (opaque `Db`, RLS as the user); never build queries in pages. Data modules take typed input, return domain types (`lib/inventory/model.ts`, row types such as `lib/finance/entry-rows.ts`; client components import types/constants from `lib/finance` or `lib/inventory`, never values from `lib/server`), throw `DataError`, and don't import `next/*`. Validation (`InputError`), `revalidatePath` and `redirect` stay in the action; `runAction(guard, work)` in `lib/action.ts` turns errors into `ActionResult`. Writes are the audited SQL functions via `rpc()` (argument names checked against generated types). New queries use `sb(db)` (typed); finance queries moved as-is use `untyped(db)`. `serviceDb()`/`serviceClient()` (secret key) only in `lib/server/users.ts` and scripts. Auth (code, link, sign-out, proxy refresh) only through `lib/server/auth.ts`.
- Registro rápido (`/rapido`, 049): phone screens shared by the modules, each part shown to the module's editors: lançamento financeiro (`/rapido/lancamento`: one rubrica, sign from the rubrica's kind, account = payment method default or "A definir", optional receipt upload after saving when attachments are on; `create_quick_ledger_entry`), associado novo (`/rapido/associado`: `AssociateForm quick`; `associates_create_quick`) and the inventory actions (`/rapido/inventario/[id]?acao=…`, `/rapido/inventario/novo`; `inventory_quick`). Actions in `app/(gestao)/rapido/actions.ts`; confirmation `?feito=<tipo>&id=` (`lib/quick.ts`). Everything enters for real and stays "para revisar" (`review_status` on `ledger_entries` and `associates`, inventory movements as before); each module reviews in its own list: Financeiro `?revisao=para_revisar` pill + "Revisar" mark + bulk "Marcar revisados" + notice on the entry (`review_ledger_entries`), Associados `/associados?revisao=para_revisar` + notice on the profile (`associates_review`), Inventário Movimentações › Para revisar. Início counts them. Old `/inventario/rapido/*` URLs redirect.
- Session: `lib/server/session.ts` is the only file that reads `memberships`. `Member` has `db`, `user { id, email }`, `isAdmin`, `finance { role, canEdit }`, `inventory { role, canEdit, canManage }` and `associates { role, canEdit }`; guards `pageSession`, `pageMember`, `memberOrError`, `financeEditorOrError`, `inventoryEditorOrError`, `inventoryManagerOrError`, `associatesEditorOrError`, `adminOrError`, `requireFinanceEditor`, `requireAssociatesEditor`, `requireAdmin`.

## gestao › financeiro

- Supabase Auth passwordless, restricted to `@escoteirosalbert.com.br`; RLS per group.
- Money stored as integer cents (`lib/money.ts`).
- Migrations in `supabase/migrations/`.
- Model (glossary in `apps/gestao/docs/modelo.md`): `ledger_entries` = entry (date, `name` shown as "Histórico", account, payment method, `document_filed`, total); `entry_splits` = per-category split with description and optional associate; `statement_lines` = imported OFX lines (`external_id` = FITID, "ID OFX"), linked to entries via `reconciliation_links`. `categories.code` is derived from `parent_id` + `position` by `renumber_categories` (036): never write or hard-code it (except roots `1`/`2`); reference rubricas by id. The Rubricas screen is a client draft (`lib/category-draft.ts`) saved in one call to `save_category_tree`. `categories.ledger_code` / `accounts.ledger_code` = accounting chart code (domain `ledger_code`, mask `0.0.0.0.0000`, mirrored in `lib/ledger-code.ts`).
- All writes go through audited SQL functions (no direct write policies on catalogs, accounts, entries or statement tables). List views read `ledger_entry_rows` / `entry_split_rows` (security_invoker, with `external_ids` and `search_text`).
- Paths below under `lib/` are in `lib/finance/` unless they are the shared ones listed in the gestao section.
- Statement import is OFX-only; the CSV statement import code was removed for good (`lib/csv-reader.ts` is only the generic reader for the associates CSV import). Exports: column definitions in `lib/export/columns.ts`, rendered as XLSX or CSV; accounting CSV at `/financeiro/exportar/contabil` (see `docs/contabilidade.md`).
- SQL tests: `supabase/tests/*.sql`, run inside a rolled-back transaction (see each file's header).
- Routes: module = 1st segment, menu item = 2nd, header tab = 3rd (`/financeiro/lancamentos/movimentacoes|detalhamento|realizado`, `/financeiro/extrato/conciliar|importar`, `/financeiro/mensalidades/controle|devedores`, `/financeiro/configuracoes/<aba>`; associates, sections and the associates CSV import live in `/associados`, and `/financeiro/configuracoes/associados` redirects there); query string only for filters and display modes. Area roots redirect to the first tab; the module root `/financeiro` is the finance Resumo (year totals, account balances today, month by month, recent entries, overdue fees) and the menu starts with "Resumo". Every finance page header gets "Financeiro" after Início in the breadcrumbs (wrapper `PageHeader` in `components/finance/nav/page-header.tsx`). Movimentações and Detalhamento share `app/(financeiro)/financeiro/lancamentos/entries-screen.tsx`; `voltar` carries the list path + filters (`listHref` in `lib/entries.ts`). The `rubrica` filter is compact (`id` = subtree, `-id` = excluded subtree; `encodeCategorySelection`).
- Screens: every page header uses `PageHeader` (`components/finance/nav/page-header.tsx`: title, `SectionTabs` beside it, actions on the right, description, filter rows as children) inside `PageBody`/`PAGE_BODY`; never hand-roll an `<h1>` row. Every page except Início passes `crumbs` (path after Início, ending in the current page; `settingsCrumbs`/`extratoCrumbs` helpers); links back carry the filters. Breadcrumbs keep the title in the same place on every page; no separate "Voltar" link. Início has no breadcrumbs and a screen-reader-only title (`hideTitle`): only the actions row shows.
- Forms: every input, select and textarea has a visible label (`<Label htmlFor>`). Placeholders only show examples, never replace the label; `sr-only`/`aria-label` alone is not enough. Exception: search fields with the magnifier icon keep only `aria-label` and a placeholder. In editable table rows, the visible column header is the label (keep a specific `sr-only` label per row).
- `npx supabase migration up` applies new migrations without resetting local data.
- Attachments (receipts, 027) are switched off by a feature toggle: `ATTACHMENTS_ENABLED` in `lib/features.ts` (`NEXT_PUBLIC_FEATURE_ATTACHMENTS=on` turns them on, read at build time). Off: no upload/remove (actions refuse), download route 404, no Comprovantes section, no paperclip in the lists, no receipt field in `/rapido/lancamento`; e2e attachment steps are skipped. The tables, bucket and code stay.

## gestao › inventario

- Model and vocabulary in `apps/gestao/docs/inventario/modelo.md` (material by unit with tag `GEAS-000-0000` or by lot; divisions as a tree; families with 3-digit code; movements with review status). Read errors show `app/(inventario)/inventario/error.tsx`.
- Review (044): `review_status` is `para_revisar` | `revisado`. Chief movements and every movement from the quick screens start `para_revisar`, even the manager's/admin's; managers review (also their own) via `inventory_review_movements` (Movimentações › Para revisar, bulk with optional note; or per row in the material history; `components/inventory/review.tsx`). No rejection: wrong entries are fixed with a normal movement.
- Lots merge (046): a lot is material + division + condition + expiry + `variant` (optional text, e.g. "modelo antigo"); `inventory_add_lot`, transfers and condition changes add into a matching lot (`inventory_matching_lot`, unit value by weighted average, entry data kept in the movement `details`) instead of creating another.

The Materiais list has one ± button per row for lot materials: dialog with Remover (write-off with lot choice, soonest expiry first; default when there is stock) / Incluir (new lot in that division) in `components/inventory/materials/withdraw.tsx`.
- Quick entry for phones (045): inventory part of the shared `/rapido` (search, `/rapido/inventario/[id]?acao=retirar|entrada|condicao|transferir|ajustar`, `/rapido/inventario/novo`), editors only; writes only through `inventory_quick(p_action, p_args jsonb)` (sets `inventory.channel = 'rapido'` for `inventory_log`; arg names in `lib/server/inventory/quick.ts`). Loans/returns: not built yet (BACKLOG).
- Division order is chosen by the manager by dragging (`inventory_locations.position`, `inventory_place_location` 037: before/after/inside, saved on drop), never alphabetical: sort by `sort_key` from `inventory_location_paths` (`treeOrder` in `lib/inventory/locations.ts`).
- Dev data from the group's spreadsheet: `apps/gestao/scripts/inventory/planilha-para-csv.mjs` then `importar-planilha.mjs` (local Supabase only; wipes and reloads the group's inventory). The CSVs are group data: never commit them.

## Shared UI (`packages/ui`, `@geas/ui`)

- Same identity in every internal app: build screens from `@geas/ui`, never hand-rolled CSS classes or app-local copies of primitives.
- `@geas/ui` (root export): app shell — `AppBrand` (module switcher: `current` is `gestao | financeiro | inventario | associados`, any number of modules, logo goes to `homeHref`), `AppLogin`/`AppLoginForm`, `AppHeader`, `UserMenu`, `PageHeader`, `PageBody`, `SectionTabs` (pill buttons; below `sm` a menu button with the active tab, `components/section-tabs-menu`); `AppHeader` shows a menu button (`components/app-nav-menu`) below 1024px; `utilities` are `{ href, label, icon, active }`.
- `@geas/ui/components/<name>`: shadcn/ui (`base-mira`, Base UI primitives — not Radix) plus `section-card`, `stat-card` (`StatCard`, `ListCard`), `option-controls` (`OptionSelect`, `OptionCombobox`) and `tree-drag` (`useTreeDrag`, `DragHandle`: drag rows of a tree table before/after/inside; used by Rubricas and Divisões). Reorder only by dragging: no up/down arrows. Add shadcn components with `npx shadcn@latest add <name>` inside `packages/ui`. Imports inside the package use `@geas/ui/...` (self-reference), never `@/`.
- `@geas/ui/lib/utils` (`cn`) and `@geas/ui/lib/use-action-toast` (Server Action result → toast).
- Forms with typed fields use `ActionForm` (`@geas/ui/components/action-form`), never `<form action={…}>`: React 19 resets uncontrolled fields after every action, even on error. `ActionForm` submits via `onSubmit` + transition and clears only when `result` (the `useActionState` state) has no `error`. Plain `<form action>` only for hidden-field forms (toggle, remove).
- Cards: every card surface (SectionCard, StatCard, ListCard, hand-made panels) uses the `surface` utility from `theme.css` (soft 1px border, card background); never hand-roll `rounded-lg border bg-card` or dark borders. Inner dividers stay `border-b`. `html` reserves the scrollbar gutter (no layout jump). Choice between a few options with explanations: `radio-group` as choice cards (`FieldLabel` > `Field orientation="horizontal"` > `FieldContent` + `RadioGroupItem`), side by side from `sm`, stacked below; e.g. Controle in the material form. In two-column form grids use `items-start` so a help text under one field does not push the label of its neighbour.
- Users: `@geas/ui/lib/roles` (domain, group/inventory roles) and `@geas/ui/components/users-manager` (screen with one role column per module). Data (list, invite, roles, remove) is `apps/gestao/lib/server/users.ts`; `/usuarios` actions check the admin and revalidate. `@geas/ui` has no database code.
- Theme: each app's `app/globals.css` starts with `@import "@geas/ui/theme.css"` (Tailwind, tokens, shell CSS in `@layer components`, legacy CSS in `@layer legacy` below utilities) and the root `<html>` carries `data-app="gestao" | "financeiro" | "inventario" | "associados"` (in gestao, set by each module root layout), which sets the accent (`--app` → `primary`/`accent`: purple / dark orange / green `#0b7a4b`). ## Commits and GitHub rules

Full rules in `CONTRIBUTING.md`. Conventional Commits in English, checked by commitlint (`commitlint.config.mjs`; scopes `gestao`, `financeiro`, `inventario`, `ui`, `institucional`, `db`, `e2e`, `deps`, or none) through the husky `commit-msg` hook and the `Commit messages` check. PRs are squash-only (PR title = commit on `main`). Rulesets on `main`: "main: integridade" (no deletion, no force-push, linear history, no bypass) and "main: PR e checks" (PR + required checks, admin bypass). Required check names are the job `name`s in `ci.yml` and `commits.yml`: renaming one means updating the ruleset.

## CI/CD

`.github/workflows/ci.yml` runs on push to `main` and on PRs: job `checks` (lint, typecheck incl. `astro check`, vitest, build) and job `db-e2e` (local Supabase via CLI 3.1.0, `supabase test db`, Playwright). `.github/workflows/commits.yml` runs commitlint on PR titles and on commits pushed to `main`. No CD for the site: it is deployed by manual FTP to a host we don't own; don't add deploy steps or rely on host config files like `_redirects`.

Production: nothing of `apps/gestao` is in production yet (2026-11-19); every migration exists only in development, so migrations may be edited or consolidated (that needs `supabase db reset`, which wipes local data such as the inventory imported from the spreadsheet). The Supabase and Vercel Git integrations are disconnected, so nothing deploys or migrates on push. Supabase is being left (`docs/migracao-saida-supabase.md`), so its dashboard paths and auth URLs are not updated for `apps/gestao`. Hosting of the internal app is under evaluation and will not be Vercel: don't add deploy steps or host-specific config. Never `supabase config push` (`config.toml` is local only).
